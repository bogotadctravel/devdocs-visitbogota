2. Tema y constructor visual​

El proyecto utiliza Bricks Child Theme como tema activo y Bricks como tema padre. Esta arquitectura es correcta: las personalizaciones del proyecto se mantienen en el tema hijo, mientras que el tema padre puede actualizarse sin sobrescribir cambios locales.

Función del tema hijo​

El tema hijo permite agregar CSS, funciones PHP y elementos personalizados sin alterar el tema padre. Este enfoque es una buena práctica en WordPress porque reduce el riesgo de pérdida de cambios durante actualizaciones.

A partir de la captura del editor de temas se identifica una estructura mínima con style.css, functions.php y el directorio elements/title.php. Esto indica que el proyecto no depende de un tema PHP tradicional con múltiples templates; la mayor parte de la experiencia se genera desde Bricks.

ArchivoResponsabilidad documentada
style.cssHoja de estilos del tema hijo. Carga después de bricks-frontend.
functions.phpRegistra estilos del child theme y elementos personalizados de Bricks.
elements/title.phpElemento personalizado registrado dentro del constructor Bricks.

3. Personalizaciones detectadas en functions.php​

La captura del editor de archivos del tema permite identificar funciones relevantes dentro de functions.php. Estas personalizaciones son pequeñas pero importantes para entender cómo se extiende Bricks en el proyecto.

Registro de estilos del tema hijo​

El código registra el archivo CSS del tema hijo mediante wp_enqueue_scripts. Se usa wp_enqueue_style con dependencia de bricks-frontend, lo que asegura que el CSS personalizado se cargue después de los estilos del tema padre.

El uso de filemtime() funciona como versionado automático del CSS. Cada vez que cambia style.css, cambia el número de versión del recurso y el navegador recibe el archivo actualizado, evitando problemas de caché durante desarrollo o ajustes visuales.

Registro de elementos personalizados de Bricks​

El archivo registra un elemento personalizado mediante Bricks\Elements::register_element(). El elemento encontrado está en /elements/title.php.

Esto confirma que el proyecto no se limita a usar elementos nativos del constructor: existe al menos un componente propio registrado para la landing. La documentación de title.php requeriría abrir ese archivo para explicar propiedades, controles y salida HTML.

Categoría personalizada en el builder​

Se añade una cadena de traducción al builder para una categoría denominada Custom. Esto permite agrupar elementos propios dentro de Bricks y separarlos de los elementos estándar.

4. Plugins activos​

El sitio mantiene una configuración de plugins extremadamente liviana. En la versión actual de la documentación se conserva únicamente GTM4WP como plugin activo documentado.

PluginVersiónFunciónCriticidad
GTM4WP1.22.3Integra Google Tag Manager con WordPress sin modificar el tema. Permite administrar medición, eventos y conversiones desde GTM.Media

GTM4WP conecta el sitio con Google Tag Manager. Esto permite gestionar medición y eventos sin intervenir archivos del tema. En una landing de conversión, el uso recomendado es medir: clics en CTAs, envío del formulario, scroll depth, clics en menú, interacción con anclas, clics en redes y enlaces externos.
